# Browser Runtime Shell (Phase 2)

This document describes the browser-facing shell around the `re3_wasm` module built
in [docs/WASM_BUILD.md](WASM_BUILD.md). Phase 2's job is everything *between* the
browser and re3's own `main()` -- loading the module, owning the canvas, reporting
what the browser environment can and can't do, and turning failures into something
visible instead of a blank tab. It does **not** render GTA III, does not ship any
game assets, and does not add gameplay UI -- that's later phases.

```
Browser
   |
web/index.html                  <- page shell: canvas, loading UI, diagnostics, log
   |
web/launcher.js                 <- instantiates the module, owns the canvas/resize/
   |                                fullscreen, reports diagnostics, catches failures
Emscripten WASM (build/re3_wasm.js + .wasm)
   |
re3 initialization (C++ main(), unmodified from Phase 1)
   |
controlled shutdown / error     <- caught by launcher.js, shown in the UI
```

## Directory layout

```
web/
    index.html      Page shell: topbar, canvas, loading overlay, error banner,
                     diagnostics + log side panel. No gameplay UI.
    launcher.js      All runtime logic (module bring-up, canvas/resize/fullscreen,
                     diagnostics, error handling). Vanilla JS, no build step, no
                     dependencies.
    styles.css       Styling for the above.
    build/           Generated by `cmake --build build-wasm --target re3_wasm`
                     (re3_wasm.js + re3_wasm.wasm). Not committed source -- rebuild
                     it, don't hand-edit anything here.
scripts/
    serve_web.py     Local dev server for web/ that sends the COOP/COEP headers
                     pthreads need (see "Cross-origin isolation" below).
```

`web/` is meant to be served as-is: open `web/index.html` through an HTTP server
(not `file://` -- see below) and everything it needs is already alongside it.

## Building and running

```bash
# 1. Build the WASM module (also copies it into web/build/)
cmake --build build-wasm --target re3_wasm --parallel 4

# 2. Serve web/ with the headers pthreads need
python scripts/serve_web.py 8080

# 3. Open http://127.0.0.1:8080 in a browser
```

Re-running step 1 after a source change refreshes `web/build/` automatically; just
reload the page.

### Why not `file://`?

Opening `web/index.html` directly from disk will not work: browsers block
`fetch()`/`XMLHttpRequest` of the `.wasm` file (and Emscripten's `Module.locateFile`
resolution) under the `file://` origin, and cross-origin isolation (next section) is
unavailable there regardless. Always serve `web/` over `http://`.

### Why a custom dev server instead of any static file server?

> **Update (Phase 8, `docs/THREADING_WASM.md`)**: `re3_wasm` no longer uses
> `-sUSE_PTHREADS` at all (a threading audit found the only background thread in
> the engine, CD streaming, didn't actually need real threads in a browser VFS
> and now runs synchronously) -- so `SharedArrayBuffer`/cross-origin isolation
> are **no longer required** to run it. The explanation below is kept for
> history and because `scripts/serve_web.py` still sends these headers
> (harmless, and useful if a future phase reintroduces pthreads for a
> profiled reason); a plain static file server works fine for `re3_wasm` today.

`re3_wasm` used to be built with `-sUSE_PTHREADS=1 -sPTHREAD_POOL_SIZE=4` (see
`src/CMakeLists.txt`), so it spun up a worker thread pool on load. Browsers only
allow `SharedArrayBuffer` -- which is how Emscripten hands memory to those workers
-- on a page that is [cross-origin isolated](https://web.dev/articles/coop-coep),
which in turn requires the server to send:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

on every response. `python -m http.server` does not send these, so the module load
fails immediately with `DataCloneError: ... SharedArrayBuffer transfer requires
self.crossOriginIsolated` (you can reproduce this by pointing `serve_web.py`'s
handler back at plain `SimpleHTTPRequestHandler`). `scripts/serve_web.py` is a ~30
line wrapper around Python's stdlib HTTP server that adds those two headers. This is
a **hosting** concern, not an engine one: whatever serves `web/` for real (nginx,
a CDN, GitHub Pages via a custom worker, etc.) needs to set the same two headers, or
threads won't work there either. The diagnostics panel (below) reports
`crossOriginIsolated` and `SharedArrayBuffer` live, specifically so this is
immediately visible if it's ever missing again.

## What `launcher.js` actually does

1. **Static diagnostics**, collected immediately and independent of whether the
   module ever loads: WebGL/WebGL2 support (via a throwaway canvas), WebAssembly
   support, `SharedArrayBuffer`/`crossOriginIsolated`, `hardwareConcurrency`, Worker
   support, Fullscreen API support, `devicePixelRatio`, canvas size. This is the
   "browser diagnostic mode" from the task list -- open the diagnostics panel (top
   bar button) any time, whether or not the engine got anywhere.
2. **Canvas sizing**, entirely at the DOM/CSS level, independent of the engine: the
   canvas fills `#viewport` via CSS, and its backing pixel buffer is sized to
   `CSS size * devicePixelRatio` on load, on `ResizeObserver`/`resize` events, on
   `visibilitychange` (a hidden tab's `ResizeObserver`/`requestAnimationFrame`
   callbacks are suspended by the browser until it becomes visible again -- see
   inline comments in `launcher.js`), and after entering/exiting fullscreen.
3. **Module instantiation**: `createRe3Module({ canvas, print, printErr, setStatus,
   monitorRunDependencies, onAbort })`. `MODULARIZE=1`/`EXPORT_NAME=createRe3Module`
   (set in `src/CMakeLists.txt`) is what makes this factory-function pattern
   possible instead of Emscripten's default auto-running global-`Module` shell --
   it's what lets the launcher control *when* things happen and catch failures at
   each step instead of racing a page load.
4. **Controlled main() invocation**: the build also sets `-sINVOKE_RUN=0`, so
   `main()` does not run on its own. The launcher calls `instance.callMain([])`
   itself, inside a `try/catch`, only after the module has instantiated and the
   canvas exists. This is unmodified re3 C++ startup code from Phase 1 -- the
   launcher does not special-case or stub out any of it.
5. **Error boundaries, not workarounds**: `onAbort`, the `callMain()` catch block,
   `window.onerror`, and `window.onunhandledrejection` all funnel into a single
   `showFatalError()` that updates the status dot, shows the error banner with the
   full stack, and logs to both the on-page log panel and the real devtools
   console. Nothing is caught and silently swallowed. See "Current failure mode"
   below for what this actually looks like today.

## Current failure mode (expected, not a bug)

As of Phase 2, running the module through to `callMain()` reliably reaches real
re3 C++ code and then fails, because the engine still assumes a native OS
filesystem full of GTA III game data that this shell deliberately does not fake
(task list: "Do NOT add fake GTA III assets"):

```
cdvd_stream: can't get filesystem info
RE3 ASSERT FAILED
    File: src/core/CdStreamPosix.cpp
    Line: 205
    Function: CdStreamInit
    Expression: 0
casepath couldn't find dir/file "models", full path was models\coll\peds.col
RuntimeError: null function
```

This is caught by the launcher and shown in the error banner / log panel, not left
as a crashed tab -- that's the "fail gracefully if initialization is incomplete"
requirement. Making this actually succeed is out of scope for Phase 2 and belongs
to whatever phase adds a virtual filesystem (`IDBFS`/`--preload-file`/asset
packaging) and revisits `CdStreamPosix.cpp`'s assumptions about native file I/O and
threading -- a real fix there, not a browser-shell workaround.

## Abstraction boundary (task 10)

The instruction for this phase was explicit: if the engine can't initialize because
native APIs are still involved, build a clean boundary rather than patching around
individual crashes. Concretely, that boundary is:

- **`launcher.js` never touches re3/librw source.** It treats the module as an
  opaque thing that either instantiates or doesn't, and either returns from
  `main()` or throws/aborts. It has no knowledge of `CdStreamPosix.cpp`,
  `CFileMgr`, or any other engine internal.
- **Every native-API gap surfaces as data, not a special case.** The diagnostics
  panel reports what the *browser* can do (WebGL2, threads, etc.) independent of
  engine state; the log panel shows exactly what the *engine* printed on its way
  to failing. Nothing is inferred or guessed at in JS.
- **The one thing this phase changed on the hosting side (COOP/COEP headers) is a
  real fix, not a hack**: it makes a genuinely-missing browser capability
  (cross-origin isolation) actually available, the same way any production
  deployment would need to, rather than avoiding pthreads or stubbing thread
  creation to dodge the error.

## Known limitations of this shell

- No gameplay UI, no input handling beyond what GLFW/the engine already does, no
  asset loading -- none of that is in scope yet.
- The `Fullscreen` and resize handling operate on the DOM/canvas only; nothing
  downstream in the engine has been verified to react to a live resize yet, since
  `main()` doesn't currently get far enough to reach the render loop.
- `document.hidden` (backgrounded tab) suspends `ResizeObserver`/`requestAnimationFrame`
  per spec in every standards-compliant browser -- this is expected behavior, not a
  bug, and is why the launcher also listens for `visibilitychange`/`load`/plain
  `resize` as belt-and-suspenders.
